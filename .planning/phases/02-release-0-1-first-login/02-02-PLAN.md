**Design decisions in this plan:**
- **Intent methods instead of a generic `begin() -> Box<dyn Tx>`** (ARCHITECTURE §7.1). Every multi-row change that must be atomic is one port method: `create_code` (family + code), `UserRepo::create` (user + password + token + email), `complete_recovery`, `complete_setup`, `install`. Record this deviation in §7.1 with its rationale: dyn-safe, impossible to forget a commit, and each atomic unit is contract-tested.
- **G3 / P5:** the token family is created **with the code**, so a reuse that races the exchange still revokes it. The AT carries the family id (`fid` claim, set by 02-08) and UserInfo checks `revoked_at`.
- **G2:** token_family stores user_id, client_id, scope, auth_time, acr, amr, session_id and the claims request. A refreshed ID token repeats auth_time, and UserInfo applies `claims.userinfo`.
- **G4:** standard claims are a typed `StandardClaims` struct. Backends store it as JSON.
- **G6:** verification, recovery and invitation tokens are a `self_service_token` aggregate (hash PK, kind, user_id, email, expires_at, consumed_at).
- Emails are stored normalised (lowercase, trimmed) by core. Storage enforces unique (tenant_id, email) and unique (tenant_id, username).
- Flow state and authorization params are opaque to storage: flow `state` is a `String` (JSON produced by 02-09), and `AuthorizationParams` is a serde struct that backends store as JSON.
- Every timestamp goes through `truncate_to_ms` (existing contract).
