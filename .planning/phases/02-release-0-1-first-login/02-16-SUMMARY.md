# Phase 2 Plan 16: Management API Summary

**The OpenAPI 3.1 management API at `/api/admin/v1` manages tenants, clients and users. It authenticates with system-tenant access tokens through the one `AccessTokenVerifier` and checks admin scopes. The spec is generated by utoipa-axum, served without auth at `/api/admin/v1/openapi.json`, committed as `docs/openapi/admin-v1.json`, and covered by a drift test.**

## What was built

- **Routes** (16 operations):
  - `GET/POST /tenants`, `GET/PATCH/DELETE /tenants/{slug}`
  - `GET/POST …/clients`, `GET/PATCH/DELETE …/clients/{client_id}`, `POST …/clients/{client_id}/secret`
  - `GET/POST …/users`, `GET/PATCH/DELETE …/users/{user_id}`
  - List endpoints return `{items, next_cursor}`. Create returns 201 with a `Location` header. Delete returns 204.
  - Every error is RFC 9457 problem JSON produced by `errors::problem_json`.
- **AdminAuth** checks, in order:
  1. The request must address the installation root. `/t/{slug}/…` and custom hosts get 404.
  2. The Bearer token must be in the `Authorization` header (scheme is case-insensitive, exactly one header).
  3. The system tenant is loaded through `TenantService`. The issuer is `issuer(public_url, Path("system"))`.
  4. `AccessTokenVerifier::verify` runs.
  5. The token's client must still exist.
  6. Each handler then calls `require(Resource, Access)`, which uses `scope_satisfies`.

  401 responses carry `WWW-Authenticate: Bearer realm="anvilid"`, with `error="invalid_token"` when a token was presented. 403 responses carry `error="insufficient_scope"`.
- **Handlers** only call `TenantService`, `ClientService` (with `redirect_validator: validate_redirect_uri`) and `UserService` (with `kek: AppState::kek_arc()`). They never touch storage.
- **Spec:**
  - Info: "AnvilID Management API", version v1, OpenAPI 3.1.0.
  - The `oauth2` scheme uses a `clientCredentials` flow with tokenUrl `/t/system/token` and all 8 admin scopes.
  - The 401, 403 and problem responses are documented with `application/problem+json`.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 - Security] System-tenant client writes need admin:write**
- **Found during:** Task 1
- **Issue:** A system-tenant client can hold `admin:write`. With only `admin:clients:write`, a caller could create such a client, or rotate the secret of the management client, and so gain full admin.
- **Fix:** `AdminAuth::require_full_admin()` runs for write operations on `/tenants/system/clients…`. The test `system_clients_need_full_admin` covers it.
- **Commit:** 81aa9fa

**2. [Rule 2 - Security] Access tokens of deleted admin clients are rejected**
- **Issue:** client_credentials tokens have no family, so deleting a client left its tokens valid for up to 10 minutes.
- **Fix:** AdminAuth looks up the token's client through `ClientService::get` after verification. The test `token_of_a_deleted_client_is_401` covers it.
- **Commit:** 81aa9fa

**3. [Rule 3 - Blocking] Test tokens minted without `TokenService`**
- **Issue:** `/token` (02-14) was not merged when this plan started. `TestApp` exposes storage only as `&dyn Storage`, but `TokenService` needs an `Arc`.
- **Fix:** `tests/admin_support` mints tokens with the production signing path: `open_key` with the KEK, then `sign_access_token` / `sign_id_token`. It creates system clients through `ClientRepo`. Once 02-14 landed, commit dc327d1 added an end-to-end test that registers a system client through the API, gets its token from `POST /t/system/token`, and checks that after rotation the old secret gets `invalid_client` at `/token`.
- **Files:** `crates/anvil-web/tests/admin_support/mod.rs` is a new helper directory that was not in `files_modified`. It follows the `token_support/` convention and no other plan touches it.

**4. [Rule 2 - Correctness] Body and query rejections are problems**
- **Fix:** Axum's default plain-text rejections are replaced by the `AdminJson` and `AdminQuery` extractors, which return problem responses. A catch-all route returns a 404 problem for unknown `/api/admin/v1/*` paths.
