**Facts from RESEARCH (suite @246b2c1; re-check the Basic plan module list at the pinned CONFORMANCE_TAG before starting, because the suite changes weekly):**
- The suite trusts any certificate (trust-all TrustManager). Config OP fails if any `*_endpoint` is not https.
- Static clients: config sections `client`, `client2`, `client_secret_post`, each needing the exact redirect URI `https://localhost.emobix.co.uk:8443/test/a/{alias}/callback`.
- The browser automation (HtmlUnit, no JS needed) fills `#identifier` and `#password` and clicks `#login-submit`. Overrides for `oidcc-prompt-login` and `oidcc-max-age-1` (second login page, `update-image-placeholder-optional`) and for `oidcc-ensure-registered-redirect-uri` (wait for the error marker text "The redirect URI in this request is not registered for this client", then `update-image-placeholder`). Model these on `.gitlab-ci/local-provider-oidcc-conformance-config.json` in the suite repo.
- The `acr_values` module requests values from `acr_values_supported` and expects one echoed in the ID token's `acr`.
- Unexpected WARNINGs fail the runner, as do unexpected skips.
- Setup via curl works because the CSRF layer allows requests with no Fetch-Metadata/Origin headers (GET /setup → csrf_token + flow cookie from the HTML/cookie jar → POST).

**Security/hygiene:** generated secrets, the cert/key and the config live only in `$RESULTS_DIR/tmp` (gitignored) and are deleted on exit. Never print secrets in logs.
The admin user password is random per run.
