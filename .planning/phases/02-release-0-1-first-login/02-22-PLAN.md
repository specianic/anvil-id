**Design (decided by the orchestrator):**
- Keep the storage port and schema unchanged: `NewEmail.payload` / `OutboxEmail.payload` stay a
  `BTreeMap<String, String>`. A sealed payload is represented as a single entry
  `{"sealed": "<base64url of Kek::seal(PURPOSE, aad, json_bytes)>"}`, where `PURPOSE = "anvilid/outbox-payload/v1"`
  and `aad` = tenant id bytes. (Do not use the outbox row id in the AAD — it is not known when the email is built.)
- Add to `model/outbox.rs`: `pub fn seal_payload(kek: &Kek, tenant: TenantId, payload: &BTreeMap<String,String>) -> Result<BTreeMap<String,String>, CoreError>`
  and `pub fn open_payload(kek: &Kek, tenant: TenantId, stored: &BTreeMap<String,String>) -> Result<BTreeMap<String,String>, CoreError>`.
  `open_payload` rejects any map that is not exactly one `sealed` entry (no plaintext fallback — every row is sealed).
- Every place that builds a `NewEmail` (FlowService: verification, recovery, password-changed; UserService: invitation)
  seals its payload. These services need access to the KEK: add an `Arc<Kek>` field to `FlowService` and `UserService`
  (and update their constructors and unit tests). Wiring in anvil-web/anvilid is NOT in this plan's files: if
  `crates/anvil-web` or `crates/anvilid` construct these services, note the new constructor argument in the SUMMARY
  for 02-18 (binary wiring) and the wave-3 plans; do not edit their files.
- `anvil-mail` worker: takes an `Arc<Kek>` and calls `open_payload` before `render`. On failure: `mark_failed`
  with error text `"payload could not be decrypted"`; never log the stored value.
- anvil-mail already depends on anvil-core / anvil-jose transitively? If `anvil-jose` is not a direct dependency of
  anvil-mail and is needed, use the `Kek` re-export via anvil-core if one exists; if a manifest change is unavoidable,
  stop and record it in the SUMMARY instead of editing Cargo.toml/Cargo.lock (owned by 02-01).
