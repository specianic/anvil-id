# Phase 07.1 Plan 13: Sign-in screens (reload-safe recovery codes, one email field, link confirmation) Summary

**Recovery codes from a required in-flow MFA enrolment now live KEK-sealed in a flow and are shown on a no-store GET page that survives reload until "I have saved them, continue". The sign-in page has one address field, initial focus and a clear empty-submit message, and the upstream link confirmation's copy matches its prefill and follows PRG.**

## Performance

- **Duration:** about 3 h
- **Completed:** 2026-11-28
- **Tasks:** 3
- **Files modified:** about 40 (3 created)

## Accomplishments

- **Recovery codes (U-H7):** the confirming enrolment code answers 303 to `/ui/login/recovery-codes?flow=` with the session cookie and a new flow cookie. The GET (flow cookie required) shows the 10 codes, `no-store`, with the same codes on every reload. The confirm POST (cookie + derived CSRF) deletes the flow, clears the cookie and continues to the app. Without the cookie, with another flow's cookie, or for an expired or confirmed flow, the page shows no codes and offers a way forward (`recovery_codes_flow.gone`, account link and sign-out).
- **Sealing:** only `{"kind":"recovery_codes","sealed":…}` is stored. The seal uses purpose `anvilid/flow-recovery-codes/v1` with AAD tenant ‖ flow and also covers the return target. Plaintext scans on SQLite (file, WAL, checkpointed file, every column) and Postgres (every column) prove that no code, normalised code, joined code list or invitation token is stored in plaintext.
- **otpauth (U-M13):** `#link-otpauth` (auto-escaped) next to the QR code. The enrolment page is now `no-store`.
- **Sign-in page:** one `input[type=email]`. `#email-code-request-submit` is inside the sign-in form (U-M7). The first visible field has `autofocus` on login.html and login_identify.html (U-L2). An empty submit gets "Enter your email address." or "Enter your password." (U-L1). The MFA copy now says "This service requires…" (U-L3).
- **Link confirmation (U-M9, U-M1):** the copy and the prefill now agree. A failed confirmation answers PRG to `/ui/login?flow=`, and Cancel keeps `request=`.
- **saml.rs:** the InvalidRequest restart now uses `restart_login_in` with `NavContext::from_flow`. The request-free `restart_login` wrapper is removed (no other users).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Held codes in a new flow, not the login's own flow.** The engine deletes the login flow at CreateSession/UpgradeSession, and the headless API depends on that and on codes in its JSON. The browser layer therefore creates a separate held-codes flow, which keeps the API unchanged. The service/upstream.rs guard maps a held flow to "already finished" (InvalidRequest) instead of a corrupt-state error.

**2. [Rule 3 - Blocking] Tests outside files_modified migrated** (the behaviour change broke them, and no wave-3 plan owns them, except where noted): `flow_mfa_policy.rs` (codes page, copy), `flow_nav.rs` (link-page PRG), `hrd_login.rs`, `security_email_code.rs`, `email_code_support/mod.rs` (the email-code request now posts `identifier` to the button's formaction, like a browser), `flow_email_code.rs` (07.1-14's file, at the orchestrator's request: the codes 303 and the one-field assertions), e2e `lib/email-code.ts` (fills `#identifier`; used by 07.1-14's email-code specs) and `saml-interop.spec.ts` (confirm button).

**3. Plan said "font-mono" for codes:** they render as `<code>` in `.anvil-recovery-codes` like the account page. No CSS change.

**Total deviations:** 3. **Impact:** no scope creep. email_code.rs and main.ftl were not touched.
