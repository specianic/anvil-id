# Phase 07.1 Plan 18: End-user journeys and cross-cutting e2e Summary

**Every end-user detour (create account, registration error, forgot password, required verification, second factor and MFA enrolment Start over, email code "Use another way", upstream link Cancel) now has a browser test that starts at an app's authorization URL and must end at the fake RP with a code and the original state. Five of them also run with JavaScript disabled. A 390px sweep, axe in light and dark mode on every changed page, and a self-hosted font check complete the set. The full SQLite suite passed: 218 tests, none failed and none flaky.**

## Accomplishments

- **`lib/detours.ts`** holds the journeys, so the JS and no-JS specs run the same assertions. Each journey starts with `startAtLogin` (`authorizeUrl` for the cached web client, then waits for `/ui/login?request=`). It checks `request=` with `expectKeepsRequest` on every intermediate link where the link is visible, and ends with `expectCodeAtRp` (code present, `state` unchanged, no `error`). Emailed recovery and verification links are checked for `request=` too.
- **`flow-detours.spec.ts`** (14 tests) covers:
  - the 8 detours
  - a stale `request=` on `/ui/login`, `/ui/registration` and `/ui/recovery`: 400 `flow_expired`, no password or email field, the id is not echoed, and `#link-login` works
  - the Signed in page: `#link-account` opens the account area with `#account-identity`, and `#form-sign-out` goes through the confirmation to `/ui/signed-out`
  - consent: names the account, the offline-access copy, Allow returns to the app
  - Linked: "Last used" is set after a link is confirmed during sign-in
  - consent, the account chooser and the org chooser opened without a request: error page with a way forward
- **`nojs-flow-detours.spec.ts`** (8 tests, JavaScript off, with a guard that the passkey button stays hidden) covers create account, registration error, forgot password, required verification, second factor Start over, email code "Use another way", the stale request and the Signed in page.
- **`layout-390.spec.ts`** (9 tests) checks no overflow at 390px and a way forward on:
  - sign-in (clean and failed)
  - registration (clean, refused and check-email)
  - recovery (request, sent, reset, done and used link)
  - verification (page, done and used link)
  - the not-found, unknown-client and expired-link error pages
  - root (signed out and signed in), Signed in, logout confirmation and signed out
  - consent, the org chooser and the non-member page
  - all 8 account pages, the account confirmation step (remove app access, regenerate codes) and account TOTP enrolment
  - both recovery codes pages, MFA enrolment and the second factor

  It also visits 11 console pages and opens and closes the Menu on each, plus U-L5, C-L1 and C-L5.
- **`a11y.spec.ts`** gains 8 tests after the setup checks, which still run first. Each runs axe light and dark at mobile and desktop width plus the 320px reflow check (`auditPage`). They cover:
  - Signed in, root signed in, logout confirmation and signed out
  - the expired link page, check-email with Continue, verification done, the used verification link and recovery sent with Continue
  - MFA enrolment with `#link-otpauth` and the in-flow recovery codes page
  - sign-in with email sign-in on, and the email code page
  - 5 account pages with the account header, and the confirmation step
  - the org chooser and the non-member page
  - the upstream link confirmation
  - 8 console pages, at 390px and desktop in both schemes
- **`fonts.spec.ts`:** on the sign-in page and in the console, a Hanken Grotesk FontFace is `loaded`, the body's first font family is Hanken Grotesk, and the `.ttf` answers 200. Every request goes to the instance origin.
- **`keyboard.spec.ts`:** the console tab order is skip link, tenant switcher, Sign out, then the navigation (C-L8).
