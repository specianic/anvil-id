# Phase 07.1 Plan 07: Post/Redirect/Get, derived CSRF, sealed flash, stale links Summary

**Every end-user flow form now answers a failed POST with 303 to a GET of the same flow page. The GET re-renders the step from the flow state, bound to a CSRF token derived from the flow cookie, and shows the messages and identifier/name from a sealed one-shot flash. Used, expired or unknown reset and verification links fail on GET before any input, through the read-only peek port.**

## Performance

- **Duration:** about 3.5 h
- **Completed:** 2026-11-28
- **Tasks:** 3
- **Files modified:** about 40 (5 created)

## Accomplishments

- **Derived CSRF:** the CSRF token of a cookie-bound flow is `b64url(HMAC(kek.derive_key("anvilid/ui-csrf/v1"), tenant ‖ flow ‖ cookie))`. Only its hash is stored, the same storage as before. Native token-bound flows keep a discarded random token. Core unit tests show the token is deterministic and that a token derived for another cookie, flow, tenant or KEK never validates.
- **Flash (`ui/flash.rs`):** the payload is sealed with the AEAD key for purpose `anvilid/ui-flash/v1`, with AAD tenant ‖ flow. The cookie is HttpOnly, SameSite=Strict, Path=/, Secure on https and lives 60 s. Every read clears it. `FlashValues` has only `identifier` and `name`. A flash from another flow or tenant, or a tampered one, is ignored.
- **PRG covers** sign-in, identify, the SSO choice, passkey sign-in, second factor, MFA enrolment (QR re-derived from the sealed pending secret), in-flow passkey finishes, email code, registration, recovery request, recovery reset and verification. Locks (429 + Retry-After) and CAPTCHA demands are still direct answers. The upstream link confirmation is unchanged (it is not in the PRG map).
- **The GET** (`?flow=` on `/ui/login`, `/ui/login/second-factor`, `/ui/login/email-code` (new GET route), `/ui/registration`, `/ui/recovery`, `/ui/verification`) uses `show_step`. It answers 400 when the flash carries an error and 200 otherwise, always `no-store`, with links from `NavContext::from_flow`. The factor token and email-code token are re-sealed from the flow state.
- **Stale links:** `FlowService::self_service_link_usable` trims and hashes the token the way consumption does, then peeks. A dead reset link shows the request form with "This link has expired or was already used." and a "Send a new link" button. A dead verification link shows the notice and "Go to sign in". Opening a link never consumes it; tests open a link twice and then consume it once.
- **Orchestrator follow-ups:** the 429 page now uses `too_many_requests_in` with the request locale. The security map gained 13 rows for PRG, flash and stale links, plus 21 wave-2 rows (07.1-06 table, five 07.1-08 tests, six 07.1-09 tests). `check-security-tests.sh` reports OK with 1168 pairs.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Recovery state after a dead token** (`crates/anvil-core/src/flow/recovery.rs`, not in files_modified)
- After a dead token the engine rendered the request form but left `state.reset = true`. A PRG GET would then have shown the reset form with no token. Both dead-token branches now set `reset = false`, and the existing unit test asserts it. No wave-2 plan owns the file.

**2. [Rule 3 - Blocking] Reset token in the flash**
- The plan expected `current_step` to re-emit the reset token from flow state. The flow state deliberately never stores it (unit test `get_puts_token_in_hidden_field_only`). The token travels sealed in the flash (`reset_token`, never in `FlashValues`), and tests show it is not readable in the cookie.

**3. [Rule 3 - Blocking] Tests outside files_modified migrated** because the PRG change broke them: `flow_passkey.rs`, `security_linking.rs`, `security_csp.rs`, `email_code_support/mod.rs` (no owner), plus `hrd_login.rs` and `upstream_buttons.rs` (07.1-09, done), which the orchestrator asked for. Each keeps its intent: the 303 is followed and the page is asserted, and locks are still asserted as direct 429.

**4. Test expectations that changed by design**
- `flow_nav::second_factor_get_bounce_keeps_the_request_only_for_the_flow_browser`: with the flow cookie the GET now shows the step (200, request links kept). Without the cookie it still bounces.
- `flow_recovery`, `flow_registration`, `security_csrf`: a used or invalid token now shows `links.expired` on GET. The POST refusal is still proven by posting the token through a fresh form.

**5. Commit grouping:** `login.rs`, `recovery.rs` and `verification.rs` carry Task 2 and Task 3 code, so Task 3's Rust, templates and catalogs landed in the Task 2 commit and the Task 3 commit holds the e2e specs. Snapshots were unchanged: the templates were written so existing renders are byte-identical.

## Deferred Issues

- **Resend verification:** the plan asks for a "resend verification" action on an expired verification link. No end-user resend endpoint exists. Adding one means a new enumeration-safe, rate-limited email-sending route, which is a new security surface (Rule 4). The page offers "Go to sign in" for now.
- **Failures in other plans' areas (not caused here):** `saml_login` (12 tests) and `security_par::par_request_uri_bound_to_client` assert error-page copy ("identity provider did not work", "not issued to this client") that 07.1-08 changed.
