# Phase 07.1 Plan 12: Account area reachable and leavable Summary

**A signed-out visit to any account page now signs in and lands back on that page through an exact, security-tested return_to allowlist. Every account page has a header showing the signed-in email, a POST sign-out button and, for a static client, "Back to <app>".**

## Performance

- **Duration:** about 60 min
- **Started:** 2026-11-28T04:40Z
- **Tasks:** 2
- **Files modified:** 21 (2 created)

## Accomplishments

- **return_to widened safely (U-H3).** `parse_return_target` accepts the invitation path as before, plus exactly one of `ACCOUNT_PATHS` (profile, email, password, security, sessions, apps, linked, attributes). The value must contain no `?` and no `#` and must equal a listed path byte for byte. `Debug` redacts only invitation tokens. The module docs and the ARCHITECTURE `return_to` row describe the new rule.
- **One redirect builder.** `NavContext::login_returning_to(tenant, AccountSection)` replaces the six hand-built `/ui/login` redirects and the four re-authentication `login_url`s. A nav unit test keeps `AccountSection` and `ACCOUNT_PATHS` in step.
- **Account header (U-H4).** The shared `account_header` loads the user's email through the users port. The sign-out URL comes from `NavContext` (SignOut), and an optional `client_id` goes through `NavContext::for_client`, which applies the static-only rule from 07.1-08. All six account modules and all eight pages render it, including the TOTP enrolment and recovery-code pages. `account_base.html` renders `#account-identity`, `#link-back-to-app` (only with a resolved static home) and `#form-sign-out`/`#sign-out-submit`.
- **Tests.** `account_return_to.rs` has 7 integration tests, the unit tests in return_to.rs and nav.rs were extended, and there is a new e2e spec plus an updated account.spec.ts.

### Clarifications

**1. Sign-out "POST with CSRF"**
- The account pages' settings flow and a logout flow cannot share the one flow cookie, so the header form posts to the existing end-session endpoint, like the signed-in and error pages do. That endpoint changes nothing without a verified `id_token_hint`. It redirects to the `/ui/logout` confirmation, whose POST is bound to a flow cookie and CSRF token. No new sign-out route was added (CLAUDE.md: one implementation per concern). The integration test above proves that the GET, the cross-site POST and a POST without CSRF all change nothing.

**2. Commit split**
- Both tasks touch the same six account handlers. Task 1's commit staged a HEAD-based copy that contains only the redirect changes, built with `git hash-object` and `git update-index`. Task 2's commit adds the header plumbing on top.
