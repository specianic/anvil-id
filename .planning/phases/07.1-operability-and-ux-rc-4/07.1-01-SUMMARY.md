# Phase 07.1 Plan 01: End-user flow navigation (NavContext) Summary

**Links between end-user flow pages now come from one place, `ui::nav::NavContext`, which reads the app's authorization request from the flow row. Detours, emailed links and done pages keep the request, a stale `request=` stops on GET before any form is shown, and the signed-in page offers a way forward.**

## Performance

- **Duration:** about 2h
- **Completed:** 2026-11-28T03:01Z
- **Tasks:** 3
- **Files modified:** 22 (4 created)

## Accomplishments
- `ui/nav.rs` has the API the plan specified (`UiPage`, `AccountSection`, `LiveRequest`, `NavContext`, `WayForward`, `NavLink`, `StaleRequest`), plus `from_request` and `with_return_to`. Scheme and host come from the tenant issuer, and the console URL from the public URL. Request headers never decide them.
- `links_for` is gone. Every re-render path takes the flow's request through `NavContext::from_flow`: failed POST, CAPTCHA, lock, restart, second-factor Start over, MFA enrolment, email code, magic link, upstream link Cancel and the mfa GET bounce. This also fixes the recovery link, which never carried the request before.
- Some `request=` values cannot be continued: unknown, expired, malformed or from another tenant. On GET `/ui/login`, `/ui/registration` and `/ui/recovery` they get a 400 `flow_expired` page: heading "This sign-in link has expired", a bare `#link-login`, no form, and the id is not echoed. All four variants render byte-identical pages.
- The signed-in page is still a page, not a redirect. It now shows `#link-account`, a `#form-sign-out` POST to the end-session endpoint and, in the system tenant only, `#link-console` pointing at `{public_url}/console/`.
- The core adds `&request=` to emailed recovery and verification links started from an authorization flow. `recovery.done`, `verification.done`, `registration.check_email` and `recovery.sent` render `#link-continue` ("Continue to Shop") while the request is live. `registration.check_email` names the address (`#message-sent-to`).
- Tests: 17 in `tests/flow_nav.rs` (detours, the negative tests, emailed links through to a code at the RP, expired/foreign links degrading quietly, invitation and JIT emails without a request) and 2 signed-in tests in `flow_login.rs`. A new core unit test covers the link builder.

## Decisions Made
See `key-decisions` in the frontmatter. The main one is sign-out: the form POSTs to `{issuer}/logout` with no hint, which redirects to the existing confirmation page. Starting a logout flow on the signed-in page would have put a flow cookie back right after sign-in and broken `security_cookies::completing_a_flow_clears_the_flow_cookie`.
