# AnvilID 1.0.0-rc.3: admin UX review

Scope: the admin experience only (the setup page and the console at `/console/`), walked as a new self-hoster would. Visual polish is out of scope.

Method:
- Binary: `target/release/anvilid` (rc.3) with a fresh SQLite data dir.
- Flags and environment: `--breach-check off`, `ANVILID_SAML_EXPERIMENTAL=true`, Mailpit on 12025/18225, port 18192.
- Driven with Playwright (scripts in `scripts/journeys/`), plus reading `admin-ui/src`.

No external service was contacted. The upstream OIDC connection pointed at the instance's own default tenant. Domain verification was not clicked, because it would query real DNS.

`shots/` means `ux-admin/shots/`.
"Verified in code" means I read it in `admin-ui/src` or the generated API schema. Inferences are marked as such.

The following are missing from the console entirely, although the API has them (verified in code):
- create user
- invite user at tenant level
- edit user (email, verified, status, username)
- block or disable user
- delete user
- user search (the API supports `?email=`)
- changing a tenant's user-registration (sign-up) mode after the tenant is created

## 2. Journeys as walked (step counts)

### J1 Zero-config start: 8 steps, 2 of them guesswork
1. `anvilid serve`, then find `Setup URL: …` in the log. Pretty log lines are mixed with raw JSON audit lines on stdout.
2. Natural first try: open `http://localhost:8080/`. Result: a **404 error page** (shots/j01-01-root-before-setup.png).
3. Natural second try: open `/console/`. Result: the system-tenant sign-in form, with no hint that setup is still pending (shots/j01-02).
4. Open the setup URL. The form asks for "Admin email" and "Password" (shots/j01-03).
5. Submit. "Setup complete" shows the management client ID and secret, the token endpoint and the API base. **There is no link to the console and no mention of it** (shots/j01-04).
6. Guess the console URL, or read the README, and open `/console/`. The sign-in page is titled "System" (shots/j01-06).
7. Sign in. You land on Default tenant > Users with "No users yet." and only Import/Export buttons (shots/j01-07).
8. There is no onboarding or next step, and the header shows the admin as a UUID.

Reopening the used setup URL shows "Something went wrong · The sign-in request is invalid. · Error 403" (shots/j01-05).

### J2 "Add login to my app": at least 6 clicks or fields, and the config values live on a different page
1. Clients > New client (shots/j02-02). About 22 fields on one page. Defaults: confidential, web, client_secret_basic, consent required.
2. Enter the name, then adjust the type:
   - SPA: change Client type to Public. The auth method switches to `none` automatically (good).
   - Native: change Application type to Native. The client stays **Confidential + client_secret_basic**.
3. Enter the redirect URI and click Create client.
4. The "Client created" page shows the client ID, plus the secret once with an "I have stored it" button. Links: "Open …" and "Back to clients" (shots/j02-05, j02-09).
5. Look for the issuer or discovery URL. It is neither on the created page nor on the client page. You have to go to All tenants and copy the Discovery URL there (shots/j00-20).
6. Test the login. The console offers nothing for this: you build an /authorize URL yourself or run a sample app.

M2M: uncheck Authorization code and Refresh token, then check Client credentials. Redirect URIs, scopes `openid profile email`, consent and PKCE all stay on screen (shots/j02-07).

### J3 Users
- Create: **not possible in the console** (I seeded users through the API).
- Invite: not possible (only organization invitations exist).
- Browse: the list has 5 columns, paging and no search. Clicking an email opens the user page with tabs (shots/j03-01..03).
- Reset password, reset MFA, verify email, block, delete: **not available**. The Credentials tab can remove a credential; the password row says "Changed by the user" (shots/j03-03-user-credentials).
- Sessions tab: revoke one or all (works). Roles tab: assign and remove (works). Export and GDPR export (works, in the page header).
- Import takes 5 steps: Users > Import users > choose file > "Run dry run" (dry run is on by default) > report > uncheck Dry run > "Import users" > report.
- The file picker accepts a CSV file. Each line is then reported as `invalid_record` (shots/j03-05).
- Export all: one button, NDJSON.

### J4 Connections, organizations, HRD
- Social/upstream connection, 5–6 steps (shots/j04-01..04):
  1. Connections > New.
  2. Pick a provider.
  3. Fill Display name, **Slug (manual)**, Issuer, Client ID. The secret is optional.
  4. Create.
  5. The connection page shows the redirect URI to register at the provider. It only appears after saving.
- Organization: Organizations > New > Display name + **Slug (manual)** > Create. A section nav follows: Overview, Members, Invitations, Roles, Connections, Domains, Branding (shots/j05-01..03).
- Organization SAML: Org > Connections > SAML 2.0 (Experimental). Either import metadata (XML or URL) or fill entity ID, SSO URL and certificates, then Create (shots/j05-05).
- Domain + HRD: Org > Domains > add domain. The page shows the TXT record name and value with Copy buttons, then Verify, then a routing form ("Target connection", "Route sign-ins", "Allow local password") (shots/j05-06). This flow is clear and well explained.

### J5 Settings
- **Tenants:** All tenants > New tenant (slug manual, display name, host, registration mode). You land on the new tenant's Users page with no confirmation (shots/j06-01, j06-02).
- **SMTP:** Email > SMTP settings > host, port, TLS, from, user, password > Save. The test-email form is below (shots/j06-03).
- **Templates:** Email > template > raw HTML/text and subject, Save or Reset. No preview and no language choice (shots/j06-04).
- **Login settings:** MFA policy, passwordless, linking, language, token claims and PAR all live on one page with 3 separate Save buttons (shots/j00-13).
- **Roles:** Roles > New role (name, description, permissions). Assignment happens on the user page.
- **Webhooks:** New endpoint (name, URL, events checklist, enabled). The secret is shown once.
- **Keys:** Signing keys > Rotate key > algorithm + "Activate immediately" (shots/j06-08).
- **Audit log:** filters and a table. Actor and target are raw IDs (shots/j00-08).
- **Delete tenant:** at the bottom of Login settings, behind a confirm dialog. I recorded the dialog copy in the j06 log; there is no screenshot.

## 3. Findings

### High

**H1. No way to create, invite, edit, block or delete a user in the console.** Journey J3, Users list and user page.
- Evidence:
  - The Users page offers only "Import users" and "Export all (NDJSON)" (shots/j01-07, j03-01).
  - The user page has Export, GDPR export and tabs, but no edit, delete, block or reset (shots/j03-02).
  - Verified in code: `routes/t/$tenant/users/index.tsx` and `users/$userId.tsx` never call `POST …/users`, `PATCH …/users/{id}` or `DELETE …/users/{id}`.
  - `api/schema.d.ts` documents all three: "Create a user with a password, or invite them by email", "Update a user (… status)", "Delete a user …".
- Why it hurts:
  - A core admin task is impossible without curl.
  - It also turns H2 and H3 into dead ends.
  - The README says the console manages "users".
- Recommendation:
  - Add "Create user" (with a password, or send an invite) to the Users list.
  - Add account actions to the user page: Edit profile/email, Mark verified, Send password reset, Block/Unblock, and Delete (with a typed confirmation).
- Files: `admin-ui/src/routes/t/$tenant/users/index.tsx`, `users/$userId.tsx`, new `components/UserForm.tsx`.

**H2. A second console admin cannot be added from the console, and the last-admin guard points to an impossible step.** Journey J5, system tenant.
- Evidence:
  - System tenant > Users shows only `owner@example.com` and no create button (shots/j07-01).
  - The console offers to remove your own `administrator` role. The server refuses with: "At least one active user must keep a role granting admin:write. Give that permission to another active user first…" (shots/j07-04-remove-last-admin-role.png).
  - Because of H1 there is no other user to give the role to.
  - The e2e suite itself creates admins through the API (`createConsoleAdmin`).
- Why it hurts:
  - The installation has a single point of failure.
  - The error message tells the admin to do something the UI cannot do.
- Recommendation:
  - Add "Add administrator" to the system tenant (invite by email with the administrator role).
  - Warn before an admin removes their own admin role.
- Files: `routes/t/$tenant/users/index.tsx` (system-tenant variant), `users/$userId.tsx` (UserRoles confirm copy).

**H3. Self-registration (sign-up) is open by default and cannot be changed in the console for existing tenants, including `default`.** Journey J5, Login settings and New tenant.
- Evidence:
  - The default tenant's login page shows "Create an account" (shots/j04-06).
  - Login settings shows the mode read-only: "Follow the registration setting (currently: open)" (shots/j00-13).
  - The mode can only be set in the New tenant form (`routes/tenants/new.tsx`, default `registration: "open"`). `settings/index.tsx` reads `tenant.settings.registration` but has no control for it.
  - The "Client registration" page is about dynamic client registration (DCR), not user sign-up, so the names collide.
  - The New tenant options "Invite only (admins invite users)" and "Disabled (admins create users)" (shots/j06-01) cannot be used from the console because of H1.
- Why it hurts:
  - On a fresh install, anyone can sign up to the default tenant.
  - An admin looking for "turn off sign-up" finds nothing.
- Recommendation:
  - Put a "Sign-up" section at the top of Login settings with the mode (open, invite, disabled).
  - Rename "Client registration" to "Dynamic client registration".
  - Consider a first-run checklist item for the sign-up mode.
- Files: `routes/t/$tenant/settings/index.tsx`, `settings/registration.tsx` (title), `routes/tenants/new.tsx`.

**H4. The setup success page strands the user: it has no link to the console, only API credentials.** Journey J1, `/setup` result.
- Evidence:
  - The page reads: "Setup complete … Management client ID … secret … Token endpoint … Admin API base … Use the client ID and secret with the client credentials grant…".
  - The page contains zero links (shots/j01-04-setup-success.png).
- Why it hurts:
  - The product's goal is a zero-config start.
  - The console is what most self-hosters want next, and the page never mentions it.
  - The API secret is presented as the main outcome.
- Recommendation: a primary "Open the admin console" button, with the API credentials as a secondary "For automation" block.
- Files: the server-rendered setup template, not in admin-ui. Probably the setup handler/template in `crates/anvil-web` (path not verified).

**H5. Native apps default to a confidential client with a secret.** Journey J2, New client.
- Evidence:
  - Choosing Native leaves `client_type=confidential` and `auth_method=client_secret_basic`.
  - Creating "Mobile app" with redirect URI `com.example.app:/callback` succeeds and shows "Copy the client secret now" (shots/j02-08-native-result.png).
  - `docs/guides/native-app.md` uses `client_type: public`.
- Why it hurts: a secret shipped inside a mobile app is not secret. The console silently allows the misconfiguration the docs warn against.
- Recommendation: app-type templates (see M1), or at least switch to Public/`none` when Native is chosen and warn on Native + Confidential.
- Files: `components/ClientForm.tsx`.

**H6. A new upstream connection is enabled and shown to end users before it is complete or tested.** Journey J4, Connections > New.
- Evidence:
  - "Enabled" is checked by default.
  - I saved a Generic OIDC connection with a placeholder client ID and no secret (the field says "Client secret (optional)").
  - "Continue with Corporate SSO" immediately appeared on the login page (shots/j04-06).
  - Clicking it fails with "This application is not registered." (shots/j05-00).
  - The issuer is not checked on save ("its discovery document is read at sign-in").
  - There is no "Test connection" action.
- Why it hurts:
  - The redirect URI only appears after saving.
  - So the natural workflow (save to get the redirect URI, then register at the provider) publishes a broken button to every end user.
- Recommendation:
  - Create connections disabled by default, or show the redirect URI before saving (it derives from the slug).
  - Fetch the discovery document on save.
  - Add "Test sign-in".
  - Badge a missing secret as a warning.
- Files: `components/ConnectionForm.tsx`, `routes/t/$tenant/connections/new.tsx`, `connections/$connectionId.tsx`.

**H7. The client pages don't show what the app needs (issuer and discovery URL).** Journey J2, Client created page and client page.
- Evidence:
  - The created page shows only the client ID and the secret (shots/j02-05, j02-09).
  - The client page shows no issuer, discovery URL or endpoints (shots/j02-10).
  - The discovery URL appears only on All tenants (shots/j00-20).
  - Verified in code: only `routes/tenants/index.tsx` renders `issuer` and `discovery_url`.
- Why it hurts: the "add login to my app" journey ends with hunting for config on an unrelated page.
- Recommendation:
  - Add an "Integration" card to the created page and the client page: Issuer, Discovery URL, Client ID, the secret (on creation), Redirect URI.
  - Give each value a Copy button and offer a `.env` snippet.
  - Optionally add a "Try sign-in" link.
- Files: `routes/t/$tenant/clients/new.tsx`, `clients/$clientId.tsx`.

### Medium

**M1. New client is one ~22-field form with no app-type templates.** Journey J2.
- Evidence (shots/j02-02):
  - A first-timer sees PAR, headless native, RFC 8707 resources, back-channel logout and client kind "Agent".
  - The selects use protocol identifiers such as `client_secret_basic` and `private_key_jwt`.
- Recommendation:
  - Start with "What are you building? SPA / Web / Native / Machine-to-machine", and set the right defaults from that choice.
  - Collapse the advanced sections.
- Files: `components/ClientForm.tsx`, `clients/new.tsx`.

**M2. New clients default to showing a consent screen, even for your own apps, while the docs use `skip_first_party`.** Journey J2.
- Evidence:
  - The consent select defaults to `required` ("Ask the user for new scopes").
  - `docs/guides/spa.md` and `native-app.md` register clients with `consent_mode: skip_first_party`.
- Why it hurts: your own app shows a consent screen to its own users unless the admin knows to change this.
- Recommendation: default admin-created clients to skip-first-party through the templates; keep `required` for clients created by dynamic registration.
- Files: `components/ClientForm.tsx` (`NEW_CLIENT`).

**M3. The redirect URI error message names the wrong problem.** Journey J2.
- Evidence:
  - `localhost:5173/callback` is rejected with "web clients must use https redirect URIs" (shots/j02-04).
  - Yet `http://localhost:5173/callback` is accepted. The real problem was the missing scheme.
- Recommendation:
  - Give specific messages: a missing scheme, or http allowed only on localhost.
  - Show an example under the field.
- Files: the server validation message (crate, not verified) and the hint in `ClientForm.tsx`.

**M4. The M2M form keeps irrelevant fields.** Journey J2.
- Evidence: with only Client credentials checked, Redirect URIs, Consent, PKCE, scopes `openid profile email` and the ID token algorithm all stay on screen (shots/j02-07).
- Recommendation: hide the user-facing fields when no user grant is selected.
- Files: `ClientForm.tsx`.

**M5. The root URL, the console before setup and a used setup link give no guidance.** Journey J1.
- Evidence:
  - `/` returns a 404 error page (shots/j01-01).
  - Before setup, `/console/` shows a normal-looking sign-in form (shots/j01-02).
  - A used setup link shows "The sign-in request is invalid." with a 403 (shots/j01-05).
- Recommendation:
  - Serve a small landing page at `/`, or redirect it to `/console/`.
  - Before setup, show "Setup not completed — see the server log / `anvilid admin setup-url`".
  - For a used setup link, say "Setup is already complete — sign in to the console".
- Files: server routes and templates (not verified).

**M6. There is no landing dashboard or getting-started page; the console opens on an empty Users table.** Journey J1.
- Evidence: shots/j01-07.
- Recommendation: a tenant Overview page with a checklist (first app, SMTP, sign-up mode, second admin) and the tenant's discovery URL.
- Files: `routes/t/$tenant/index.tsx`, `components/AppShell.tsx`.

**M7. The navigation is a flat list of 14 items, identical for every tenant including System.** All journeys.
- Evidence:
  - The niche "Password hash profiles" page is top-level.
  - "Login settings" also holds token claims, PAR and Delete tenant.
  - At 390px the nav takes about 240px before any content (shots/m-j07-audit-390.png, m-j01-07-console-landing-390.png).
- Recommendation:
  - Group the nav into: Applications / Users & access / Branding & email / Security / Advanced.
  - Use a collapsible menu on mobile.
  - Hide sections that don't apply to the system tenant.
- Files: `components/AppShell.tsx`, `lib/tenant.ts` (`TENANT_PAGES`).

**M8. The Users list has no search, and the audit log shows raw IDs.** Journeys J3 and J5.
- Evidence:
  - The Users page has no search input.
  - Audit rows show `admin: 01a21fb8-…` and target UUIDs, without links (shots/j00-08).
  - The Action filter is a dropdown of about 100 snake_case values.
  - The API already supports `?email=` lookup.
- Recommendation:
  - Add an email search to Users.
  - In the audit log, resolve IDs to emails and client names, and link them.
  - Use readable labels for actions.
- Files: `users/index.tsx`, `audit/index.tsx`.

**M9. The header shows the admin as a UUID.** All journeys.
- Evidence: the header reads "01a21fb8-2105-7643-94a4-4eeb781198ee" (shots/j01-07).
- Cause (verified in code): `auth/oidc.ts` requests only `openid admin:read admin:write`, so the token has no email claim and the header falls back to `sub`.
- Recommendation: request `email profile`, or fetch the admin's user record.
- Files: `auth/oidc.ts`, `components/AppShell.tsx`.

**M10. Import is NDJSON-only with no template, CSV fails with a vague message, and the dry-run report uses past tense.** Journey J3.
- Evidence:
  - CSV shows "users.csv: 2 records", then two lines of `invalid_record The line is not a valid user record.` (shots/j03-05).
  - The docs pointer is plain text: "see IMPORT-EXPORT.md in the documentation".
  - The dry-run report says "Created 1" (shots/j03-06a).
- Recommendation:
  - Detect CSV and explain that NDJSON is expected.
  - Offer an example file and link the docs.
  - Say "Would create" in dry runs.
  - Link user IDs in the report.
- Files: `users/import.tsx`.

**M11. Slugs are never filled in from the name.** Journeys J4 and J5.
- Evidence:
  - The connection save failed because the slug was empty (shots/j04-03).
  - The organization and tenant slugs stayed empty after typing a name (script output).
- Recommendation: fill the slug from the display name until the admin edits it.
- Files: `ConnectionForm.tsx`, `OrgForm.tsx`, `SamlConnectionForm.tsx`, `routes/tenants/new.tsx`.

**M12. Login settings has 3 independent Save buttons, and no form in the console warns about unsaved changes.** Journey J5.
- Evidence:
  - Login settings has 3 separate Save buttons (shots/j00-13).
  - No `useBlocker` or `beforeunload` anywhere in `admin-ui/src`.
  - The client page mixes a read-only summary with a full edit form.
- Recommendation: one save per page or a sticky "unsaved changes" bar, plus a navigation guard on dirty forms.
- Files: `settings/index.tsx`, `clients/$clientId.tsx`, `components/form.tsx`.

**M13. Destructive actions use a plain confirm dialog, including tenant deletion.** Journey J5.
- Evidence:
  - The tenant delete dialog reads "The tenant acme-staging and all its data are removed. This cannot be undone." It is reached from the bottom of Login settings.
  - The built-in `anvil-console` client page offers "Delete client" (shots/j07-05-console-client.png; I did not click it).
  - Rotating a client secret makes the old secret stop working immediately.
- Recommendation:
  - Require typing the name to delete a tenant or organization.
  - Hide or lock Delete on the built-in clients.
  - Move tenant deletion to a "Danger zone".
- Files: `components/ConfirmDialog.tsx`, `settings/index.tsx`, `clients/$clientId.tsx`.

**M14. The SMTP page can claim a server that doesn't exist.** Journey J5.
- Evidence:
  - The page says "This tenant uses the installation's SMTP server." (shots/j06-03).
  - In code, this text appears whenever the tenant has no SMTP settings of its own (`email/smtp.tsx:106`), whether or not the installation has a server.
- Inference: on a fresh install without `ANVILID_SMTP_URL`, the page claims a server that doesn't exist. My run had one set, so I did not see this.
- Recommendation: show "No SMTP server configured — verification, recovery and invitation emails can't be sent", based on the real state from the API.
- Files: `email/smtp.tsx` (plus an API field).

**M15. After creating a tenant you land on its empty Users page, with no confirmation and no URLs.** Journey J5.
- Evidence: shots/j06-02.
- Recommendation: a success page showing the issuer and discovery URL, with "Create first client".
- Files: `routes/tenants/new.tsx`.

### Low
- **L1:** The tenant switcher option reads "system (System) [system]". File: `TenantSwitcher.tsx`.

- **L3:** The Clients list links the opaque client ID instead of the name, and the "Source: Static/Dynamic" column is jargon (shots/j02-11). File: `clients/index.tsx`.

  - The server enforces last-admin protection.

### Docs vs. console mismatches
- **README Quickstart** says to "sign in with the administrator you just created to manage clients, users, …". Users cannot be created, edited or deleted in the console (H1).
- **`docs/guides/native-app.md` and `spa.md`** use `client_type: public` and `consent_mode: skip_first_party`. The console defaults to confidential with consent required (H5, M2).
- **`docs/guides/oidc-app.md`** says "In the admin console (Clients, then New client) … create a client". The next thing the app needs is the issuer, and neither the guide nor the console shows it alongside the client (H7).
- **`docs/guides/spa.md`** says "Allow the SPA's origin (console tenant settings …)". The setting is under Login settings > "Authorization requests and headless sign-in", which is hard to find by name.
- **README and INSTALL** don't mention that `/` returns 404 (M5). INSTALL mentions `anvilid admin setup-url`, but the used/expired setup page doesn't.

## 4. Coverage gaps: existing e2e specs vs. these journeys, and assertions for new specs

**J1, zero-config start to console**
- Existing:
  - `qual04.spec.ts`: setup, then an API-created client, then the sample app. It never touches the console.
  - `a11y.spec.ts`: axe checks on the setup pages.
  - `console.spec.ts`: sign-in with an admin created through the API.
- Gap: no spec checks that the setup page leads to the console, signs in with the setup account itself, or covers `/` and the used-link page.

**J2, add login to my app**
- Existing:
  - `console.spec.ts`: an opaque client, its secret, and rotation.
  - `console-clients-v10.spec.ts`: the PAR and headless fields.
  - `console-tenants.spec.ts`: the discovery URL on the tenant list.
- Gap: no SPA, native or M2M client created through the console; defaults are never checked; config values on the client page are never checked; there is no test login from the console.

**J3, users**
- Existing: `console.spec.ts` (session revoke), `console-users-import.spec.ts`, `console-roles.spec.ts`.
- Gap: no spec for create, invite, edit, block, delete or search (the features don't exist), and none for the CSV error path.

**J4, connections, organizations, HRD**
- Existing: `console-connections.spec.ts`, `console-orgs.spec.ts`, `console-org-sso.spec.ts`, `hrd.spec.ts`.

### Running the review scripts
`scripts/` holds:
- `playwright.config.ts`
- `journeys/*.spec.ts`
- symlinks to `tests/e2e/lib` (as `lib`), `node_modules` and `fixtures`

`journeys/shared.ts` contains the helpers that would move into `tests/e2e/lib`: `consoleSignIn`, `nav`, `shot`, `mainText` and the state file.

Environment: `ANVIL_URL`, `SETUP_URL`, `SHOTS`, `UX_STATE_FILE`.

Run order:
1. Run `j01-first-run` first. It needs `SETUP_URL` and writes the admin and the management credential to `UX_STATE_FILE`.
2. Then run any of the rest:
   - `j00-sitemap`
   - `j02a`, `j02b`, `j02c` (clients; `j02c` uses the clients `j02b` creates)
   - `j03-users`
   - `j04-connections`
   - `j05-orgs` (uses the connection from `j04`; stops at domain Verify, which needs the mock DNS from `run.sh`)
   - `j05b-org-domain`
   - `j06-settings`
   - `j07-system-admins`
   - `j07b-lockout-guards`

The scripts are exploratory: they log page copy and take screenshots but assert nothing. The assertions above are what the ported specs should check.
