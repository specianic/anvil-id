# Phase 07.1 Plan 15: Console user management, second administrator, CSV import, readable audit Summary

Admins can now run the whole user lifecycle from the console: create (with a password or an invitation), search by exact email, edit, verify, block, reset password and MFA, and delete. In the system tenant they can add a second administrator in one step. Import accepts CSV, converted in the browser and posted to the existing NDJSON endpoint. The audit log shows labelled, grouped actions and resolves actors and targets to readable, linked names.

## What was built

**Task 1 (fe1ae14): users list, user page actions, Add administrator, Roles tab**
- `UserForm` has two modes: create (email, username, a password-or-invite radio, initial password, "email is verified") and edit (email, username). It uses `useFormState` + `useUnsavedChanges(isDirty && !pending)` and has a single Save. Server field errors appear next to their fields; anything else goes to a `ProblemAlert` with the server's text.
- `useSmtpAvailable(tenant)` combines system info `smtp_configured` with the tenant's `GET /smtp` (same query key and null-on-404 value as the SMTP page). `NoSmtpWarning` shows on the invite option, in Add administrator and next to the user page's password reset.
- Users list:
  - "Create user" opens a dialog; on success a status line links to the new user.
  - "Find by email" calls `?email=` (exact, case-insensitive), with a clear button and "No user has the email …".
  - An empty tenant gets an empty state with its own create button (`create-user-empty`).
  - The system tenant also gets "Add administrator".
- User page, Overview tab: an "Account actions" card with Edit (dialog), Mark email verified, Block (confirm) / Unblock, Send password reset (202 → "Reset email sent to <email>."), Reset MFA (confirm, then deletes every TOTP and passkey credential and reports what was removed), plus a `DangerZone` delete where you type the user's email. Delete navigates back to the list. Refusals, including the last-administrator 409, go through `RoleProblem`/`ProblemAlert` with the server's message.
- `AddAdministrator`:
  - It first looks the email up in the system tenant. A new address gets `createUser { invite: true }` and then `PUT …/roles/administrator`.
  - An existing account gets "already has an account … Assign the administrator role to this user instead?" and then the role assignment.
  - If the role assignment fails after the invite, retrying finds the user and offers the assignment.
- Roles tab:
  - Removing your own `administrator` role in the system tenant opens "Remove your own administrator role?". It explains the console lockout and the last `admin:write` holder rule before any request is sent.
  - The role select is hidden when nothing can be assigned (C-L5). In its place: "This tenant has no roles yet." or "The user holds every role of this tenant." with a Manage roles link.

**Task 2 (272649e): CSV import and readable audit log**
- `csvToNdjson(text)` parses RFC 4180:
  - quoted commas, quotes and newlines; CRLF/LF line ends; the BOM is ignored;
  - header columns are checked against the NDJSON record schema; unknown or duplicate columns are refused, and so is a column that is the prefix of another (e.g. `password.hash` + `password.hash.hex`);
  - the email column is required; field counts are checked per row; booleans and integers are parsed;
  - every problem carries its CSV line number (at most 50, sorted). It also returns the CSV line of each record (`sourceLines`).
- Import page:
  - CSV is detected by extension or by a first line that does not start with `{`, and converted before upload. Errors are listed as "Line N: …" with nothing uploaded.
  - The 1 MiB and 1,000-record limits apply to the converted NDJSON (a `.csv` file up to 4 MiB is read).
  - The report shows a "CSV line" column for converted files.
  - Dry-run wording: "Would create / Would update / Would skip (unchanged)" in the counts and row badges. A real run says "Created / Updated / Skipped".
  - A link to the docs and a "Download example CSV" button (Blob in the browser).
- `audit-labels.ts`: `AUDIT_ACTIONS: Record<AuditAction, { label; group }>` covers all 111 actions in sentence case, grouped into Sign-in, Users, Clients, Connections, Organizations, Settings, Keys, Webhooks and System. It replaces `ACTION_SET` in the audit page.
- Audit page:
  - The action filter is a select with optgroups.
  - Action cells show the label with the raw name in a muted mono span.
  - Actor and target cells resolve to an email or client name linked to the user or client page; actors carry an "Admin:/User:/Client:" prefix.
  - Unresolved ids are shortened (`abcd1234…`, full id in `title`). The details drawer has `CopyField`s for the actor id and target id.

**Task 3 (30a2d57): e2e specs**
- `console-users-lifecycle.spec.ts` (default tenant, unique addresses): create with a password, list status, search (uppercase input), no-match message, clear; invitation through Mailpit with a `/ui/recovery?token=` link; edit the email (heading updates, saved as unverified), mark verified (API check); block, where a fresh context's sign-in gets `login.invalid_credentials`; unblock; the user enrols TOTP on the account page; Reset MFA removes it (API check, password kept); the password reset email arrives with the recovery link; a wrong-case typed email keeps delete disabled, the exact one deletes it (API 404); the audit row "User deleted"/`user_deleted` links the admin's email, and the deleted target is shortened. Axe runs on the create dialog, invite state, search results, user page, block confirm, delete dialog and audit page.
- `console-admins.spec.ts`: Add administrator by invite (role checked through the API), then the invited person sets a password from the email, signs in to the console, sees their email in the header and loads system users. An existing system user is offered and given the role. Removing your own administrator role shows the warning (it mentions `admin:write` and adding another administrator); Cancel keeps the role. Users the spec created are deleted afterwards.
- `console-users-import.spec.ts` keeps the NDJSON test and gains a CSV test: the docs link and example download; an unknown header is reported on line 1; field-count and unclosed-quote errors carry line numbers, with submit disabled and nothing created; a valid CSV (BOM, CRLF, quoted comma) gives "2 records (converted from CSV)", a dry run with "Would create", then a real run with "Created" and the users present. Both tests use their own tenant.
- `console-audit.spec.ts`: the nine optgroup labels in order, sample labels, and the filter applied through the URL; a console-created user's row links the admin's email (`/console/t/system/users/{id}`) and the target user; an API-created user's actor links to a system-tenant client page; the details drawer shows the full actor and target ids with copy buttons.

## Deviations from Plan

### Interpretation notes

**1. "audit user_deleted with email": the deleted user's email cannot be shown**
- The audit event stores only the user id (service/user.rs records no email, by design), and the user no longer exists, so the console cannot look the email up.
- The lifecycle spec checks the labelled "User deleted" row with the **administrator's** email as the linked actor, and the deleted user's id shortened (`data-resolved="false"`).
- Showing the deleted user's email would mean putting personal data in audit details. That is a server change against the documented "never the email" rule, so I left it out.

**2. Copy button for unresolved ids is in the details drawer, not in each cell**
- `CopyField` is a labelled input plus button and does not fit in a table cell. The plan forbids a second copy implementation.
- Cells show the shortened id (full value in `title`). The details drawer has `CopyField` "Actor id" / "Target id".

**3. Email change also clears email_verified**
- The API keeps `email_verified` on an email change. The console sends `email_verified: false` with a changed address, so an unproven address is never shown as verified.
- The edit form hint says so, and "Mark email verified" re-verifies it.
